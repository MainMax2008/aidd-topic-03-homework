# Investing Demo: анализ и требования

## Архитектурный стек

Investing Demo — Django-приложение для просмотра и администрирования списка акций. HTML-интерфейс обслуживается Django views и шаблонами (`dashboard/views.py`, `user/views.py`, `*/templates/`); данные хранятся через Django ORM в PostgreSQL (`config/settings.py`, `docker-compose.yml`).

- **Django** маршрутизирует запросы (`config/urls.py`, `dashboard/urls.py`, `user/urls.py`), валидирует формы, управляет сессиями и выполняет операции ORM.
- **Django REST Framework (DRF)** предоставляет CRUD API для акций. `ShareViewSet` использует сериализатор и фильтры, включены пагинация и фильтрация по умолчанию (`dashboard/api/v1/`).
- **Celery** выполняет фоновое обновление котировок: задача `dashboard.tasks.update_last_price` зарегистрирована в расписании Celery Beat каждые 10 секунд (`config/celery.py`). Beat публикует задачу, worker исполняет ее.
- **Redis** настроен как брокер Celery по адресу `redis://127.0.0.1:6379/0` (`config/settings.py`); Compose предоставляет контейнер Redis на порту 6379. Конфигурация Compose также поднимает PostgreSQL на порту 5432.
- **Внешние данные и графики:** сервисы `dashboard/services/market_data.py` и `dashboard/services/graph.py` обращаются к Tinkoff Invest API; `plotly` строит график. Команда `dashboard/management/commands/add_shares.py` загружает инструменты в базу.

Схема обработки: браузер или API-клиент → URL-маршрутизатор → Django view / DRF ViewSet → форма или сериализатор → ORM → PostgreSQL. Отдельно Celery Beat → Redis broker → Celery worker → задача обновления → сервис рыночных данных → ORM. Просмотр графика вызывает сервис внешних данных и возвращает Plotly HTML в шаблон.

## Модель данных

### Share

Модель `dashboard.models.Share` содержит:

| Поле | Тип и ограничения | Назначение |
|---|---|---|
| `id` | автоматический `BigAutoField` | Первичный ключ |
| `figi` | `CharField(255)`, уникальный | Идентификатор инструмента внешнего API |
| `isin` | `CharField(255)` | Международный идентификатор ценной бумаги |
| `name` | `CharField(255)` | Название компании |
| `ticker` | `CharField(10)`, уникальный | Биржевой тикер |
| `currency` | `CharField(20)` | Валюта котировки |
| `uid` | `CharField(255)`, уникальный | UID инструмента внешнего API |
| `last_price` | nullable `FloatField` | Последняя известная цена |
| `is_trend_high` | nullable `BooleanField` | Признак роста относительно предыдущей цены |
| `updated_at` | nullable `DateTimeField(auto_now=True)` | Время последнего изменения записи |

Уникальность `figi`, `ticker` и `uid` обеспечивает уникальные ограничения и соответствующие индексы БД. Дополнительные `db_index`/составные индексы не заданы. Других моделей предметной области и внешних ключей нет.

### Учетные записи и целостность

`user.models.User` — алиас модели, возвращаемой `django.contrib.auth.get_user_model()`; отдельная пользовательская модель не объявлена, поэтому используется стандартная Django User. Регистрация в `user.forms.RegistrationForm.save()` создает пользователя через `User.objects.create_user(email, email, password)`, то есть email также служит username. Уникальность email проверяется формой, но отдельное ограничение БД для email не задано; username стандартной модели уникален.

Связи Share с учетными записями нет: все акции общие для приложения, а не принадлежат конкретному пользователю. Веб-операции изменения требуют входа через `IsUserAuthenticatedMixin`; API разрешает чтение без авторизации и требует аутентификацию для записи. Это ограничение доступа, но не владение объектами.

## Спецификация требований

Требования ниже описывают реализованное поведение; ссылки указывают места, где оно реализовано.

1. **FR-1. Просмотр списка акций.** Система должна показывать список акций, сортировать его по названию и разбивать на страницы по 100 записей. Подтверждение: `dashboard.views.ShareListView`, атрибуты `ordering` и `paginate_by`.
2. **FR-2. Просмотр данных акции.** Пользователь может открыть страницу акции по ее ID и увидеть график котировок за предшествующие 180 дней. Подтверждение: `dashboard.views.ShareDetailView.get()` и `dashboard.services.graph.get_graph()`; значения графика запрашиваются у внешнего API, а не из локальной истории цен.
3. **FR-3. Регистрация, вход и выход.** Пользователь может зарегистрироваться по email и паролю, войти с email/паролем и завершить сессию. Регистрация проверяет формат и обязательность полей, совпадение паролей и наличие уже зарегистрированного email. Подтверждение: `user.views.RegistrationView`, `AuthView`, `LogoutView`; `user.forms.RegistrationForm` и `AuthForm`.
4. **FR-4. Управление акциями через веб-интерфейс.** Аутентифицированный пользователь может создать, изменить или удалить общую запись акции; просмотр списка и деталей открыт без входа. Подтверждение: `dashboard.views.ShareCreateView`, `ShareUpdateView`, `ShareDeleteView` и `IsUserAuthenticatedMixin`.
5. **FR-5. Работа с акциями через REST API.** Клиент может получать список и детали, создавать, обновлять и удалять акции. Чтение доступно анонимно, операции записи требуют аутентификации. Список поддерживает фильтрацию по `name`/`ticker`, поиск по `name`, сортировку по `name`/`ticker` и стандартную пагинацию DRF. Подтверждение: `dashboard.api.v1.views.ShareViewSet`, `ShareFilter`; `dashboard.api.v1.serializer.ShareSerializer`; `config.settings.REST_FRAMEWORK`.
6. **FR-6. Периодическое обновление котировок.** Celery-задача должна получать последнюю цену каждой акции, обновлять `last_price`, время обновления и признак направления цены, журналируя ошибки по отдельным акциям. Период запуска — 10 секунд. Подтверждение: `dashboard.tasks.update_last_price()` и `config.celery.app.conf.beat_schedule`.
7. **FR-7. Первичная загрузка инструментов и получение рыночных данных.** Команда `add_shares` загружает список инструментов из внешнего API и создает записи, не дублируя их; рыночные данные используются для обновления цен и построения графиков. Подтверждение: `dashboard.management.commands.add_shares.Command.handle()`, `dashboard.services.market_data.get_last_data()` и `dashboard.services.graph.get_graph()`.

## Реестр дефектов

| Область | Наблюдавшийся дефект | Статус |
|---|---|---|
| HTML-деталь акции | `Share.objects.get(id=pk)` в `ShareDetailView.get()` поднимал `DoesNotExist` и приводил к 500 при неизвестном ID. | Исправлено: используется `get_object_or_404`, неизвестный ID дает 404. |
| Права API | У `ShareViewSet` не была задана политика permissions; стандартный DRF по умолчанию разрешал анонимные изменения. | Исправлено: `IsAuthenticatedOrReadOnly`. |
| Рыночный сервис | В `dashboard/services/market_data.py` поле цены читалось с объекта ответа, хотя находится в элементе `last_prices`; пустой список и `price=None` не обрабатывались; дробная часть `nano` отбрасывалась. | Исправлено: проверяются ответ, список и цена, сумма считается как `units + nano / 10**9`; задача пропускает отсутствующую цену. |
| График и фоновая задача | График отбрасывал дробную часть цены и не проверял `candle.close`; в задаче была опечатка `detetime`, а сравнение с `None` обрабатывалось широким `except`. | Исправлено: цена графика включает `nano`, пустое значение свечи пропускается, сравнение цены обработано явно и используется имя `price_timestamp`. |
| Формы пользователя | `AuthView.post()` обращался к `form.data` до проверки валидности. `RegistrationView.post()` извлекал только `__all__` и мог упасть, если ошибка относилась к отдельному полю. `RegistrationForm.clean()` индексировал отсутствующие ключи и не возвращал `cleaned_data`. | Исправлено: невалидные формы передаются обратно в шаблон, поля проверяются безопасно; шаблоны показывают полевые и общие ошибки. |
| Внешняя зависимость | `tinkoff-investments==0.2.0b50` — prerelease beta, указанная как неработающая; код импортирует `tinkoff.invest` в рыночном сервисе, графике и команде загрузки. | Пакет удален из requirements по заданию. Интеграция с Tinkoff теперь требует отдельно доступного совместимого SDK или замены API-клиента; без этого внешние вызовы завершатся `ModuleNotFoundError`. Импорты перенесены внутрь функций/команды, чтобы отсутствие SDK не блокировало загрузку Django-приложения. |

## Зависимости и запуск

Ключевые версии закреплены явно: Django `5.2.3`, DRF `3.16.0`, Celery `5.5.3`, Redis client `6.2.0`; обновлены совместимые версии `asgiref`, `kombu`, `amqp`, `billiard`, `vine` и `django-filter`. Брокер Redis и PostgreSQL запускаются отдельно согласно `docker-compose.yml`; сервер, worker и beat также запускаются отдельными процессами по инструкциям README.

Удаление prerelease SDK выполнено по заданию, но оно не является полной миграцией внешнего API: штатной замены клиента в репозитории нет. `tinkoff` и `tinkoff-investments` не указаны в актуальном `requirements.txt`; вызовы рыночных сервисов до добавления поддерживаемого адаптера недоступны. Текущая среда также не содержит установленного Django, поэтому системные и тестовые проверки здесь не удалось выполнить; запуск Docker/dev-сервера не производился.
